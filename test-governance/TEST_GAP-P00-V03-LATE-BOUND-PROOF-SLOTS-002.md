## Exact incompatibility

Accepted CREATE plan validation requires a new target to carry registration_id=null before installation. Later, NativeDriver._source selects source_manifest with a scope containing the actual target registration ID. That ID is generated by the native registration operation and therefore cannot be truthfully frozen into a pre-V02 signed proof object.

The same temporal dependency exists for user_init_receipt, which binds the actual registration after owner initialization; c3_postchecks, which binds the post-reboot host_boot and must not predate that boot; operation_postcheck, which binds the actual operation epoch; and recovery proofs such as run_revocation/read_absence_observation, whose scopes contain durable fence/read state created by the interrupted run.

These are not implementation conveniences. They are explicit accepted-source fail-closed selectors in ProofReader/NativeDriver. Supplying guessed future values would make a signed object graph syntactically complete but semantically false.

## Conflict with reviewed TEST_CHANGE

The reviewed producer contract currently requires every transitive proof ref needed by the selected purpose to exist, hash correctly and be pinned before signing. It also states that post-V02 evidence augmentation may add only preparation/measurement/fixture/stage/result evidence roles.

Those two rules leave no legal path for the late-bound proof roles above. A static verifier cannot prove CREATE/C3/reconciliation native resolvability by requiring concrete future proofs, and it must not silently ignore them.

Machine-readable evidence: validation/evidence/V03-LATE-BOUND-PROOF-GAP-20260922/analysis.json.

## Smallest safe correction

Keep accepted product source and all business/test oracles unchanged. Revise the infrastructure contract to split:

1. immutable pre-V02 authority objects that must be concrete before signing;
2. reviewed late-bound proof-slot definitions that bind role, subject template, allowed producer, freshness, owner/native evidence class and the stage at which the concrete scope becomes knowable;
3. monotonic post-V02 policy augmentation that may add only an allowed concrete proof to a declared slot while preserving byte-identical registration/design/code/suite/approvals/plans/native-bindings/profile/executable-policy authority;
4. static verification that proves each route is either fully concrete or has every future proof dependency covered by an exact reviewed slot, never by a placeholder.

The fixture/preparation controller (or a separately reviewed validation proof controller) may materialize such proofs only after the required facts exist and before the accepted product entrypoint consumes them. This correction changes infrastructure sequencing only, not expected exits or native acceptance semantics.
